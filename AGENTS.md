# AGENTS.md — TuxAgent

Локальный русскоязычный ИИ-агент для Linux: понимает запросы на естественном языке, автономно выполняет безопасные системные задачи и запрашивает подтверждение только при необратимом риске. GUI — PyQt6.

## Текущее состояние

Этап 1 (каркас и GUI) завершён: `pyproject.toml`, плоский `src/`, тонкий `main.py`. `app.py` создаёт `QApplication`, грузит шрифты и тему (`resources/main.qss` или `resources/light.qss`), ставит глобальный обработчик ошибок и включает логирование. `main_window.py` — контроллер окна с созданием/переключением чатов, панелью задач слева и историей чатов справа; чаты сохраняются в `data/chats.json` через `chat_store.py`. `settings_dialog.py` — диалог настроек. Разметка: `ui/main_window.ui`, `ui/settings_dialog.ui`, `ui/chat_item.ui`, `ui/task_item.ui`. Логирование — `logging_setup.py`, audit-заготовка — `audit.py`. Агент и пакетные менеджеры пока не реализованы — не выдумывай существующую реализацию, создавай её по `TODO.md`.

## Окружение и команды

- Нужен Python 3.11 (`pyproject.toml`: `>=3.11,<3.12`). Системный `python3` здесь — 3.14, используй `/usr/bin/python3.11`. Глобально зависимости не ставить (PEP 668).
- `.venv` в git не хранится; создай его перед запуском.

```bash
python3.11 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt   # runtime + dev
.venv/bin/pip install -e .                      # нужен для импорта app из src
.venv/bin/python main.py
.venv/bin/tuxagent                              # entry point app:main
.venv/bin/python src/__main__.py
QT_QPA_PLATFORM=offscreen .venv/bin/pytest -q
.venv/bin/pytest tests/test_distro.py::test_detect_astra -q   # один тест
.venv/bin/ruff check .
```

- `main.py` импортирует `app`, который лежит в `src/`; запуск работает только после `pip install -e .` либо с `PYTHONPATH=src`.
- Порядок проверки: `ruff check .`, затем `pytest -q`.
- Ruff: `line-length = 100`, правила `E,F,I,UP,B,SIM`; pytest: `testpaths = ["tests"]`, `pythonpath = ["src"]`, `qt_api = "pyqt6"`, маркеры `gui` и `slow`.

## Зависимости

- `requirements.txt` — runtime (PyQt6 с пинами Qt/sip, `platformdirs`); именно это попадает в AppImage.
- `requirements-dev.txt` — runtime + `pytest`, `pytest-qt`, `ruff`; начинается с `-r requirements.txt`.
- `requirements-ml.txt` — `torch`, `transformers`, `peft`, `bitsandbytes`, `datasets`, `accelerate`, `trl`; только ПК с RTX 2070. Torch ставить CUDA-сборкой с официального index-url, версия должна совпадать с пином. ML-стек не добавлять в runtime и не ставить на ноутбук.
- Версии зафиксированы через `==`; не ослаблять пины без причины.

## Структура и упаковка

```text
main.py                  # тонкий лаунчер
src/
  __main__.py            # python src/__main__.py
  app.py                 # QApplication, загрузка .ui/.qss
  chat_store.py          # история чатов в data/chats.json
  config.py              # настройки приложения
  logging_setup.py       # файловое логирование в data/logs
  audit.py               # audit-журнал JSONL
  main_window.py         # контроллер главного окна
  settings_dialog.py     # контроллер диалога настроек
  agent.py               # агентный цикл
  llm.py                 # LLMBackend: mock, llama.cpp, Ollama
  distro.py              # определение дистрибутива
  package_managers.py    # apt, dnf, pacman, zypper, ALT
  tools.py               # типизированные инструменты
  safety.py              # политика, верификация, dry-run
  version.py             # __version__
ui/                      # только *.ui (Qt Designer)
resources/               # *.qss, иконки
tests/                   # pytest, фикстуры
data/                    # runtime: логи, audit, кэш; в git не хранится
```

- `src/` — плоский каталог модулей, не пакет. Импорты вида `from app import main`, entry point `app:main`.
- При добавлении модуля обязательно впиши его в `[tool.setuptools] py-modules` и в `known-first-party` ruff, иначе установленный пакет/entry point его не увидит.
- Не создавать подпапки без необходимости и не добавлять зависимости с именами `app`, `config`, `tools` и т.п., чтобы не перекрыть модули.
- Модели хранить в `~/.local/share/tuxagent/models` (XDG), не в репозитории.

## GUI

- Разметка — только `ui/*.ui` (Qt Designer), стили — только `resources/*.qss`. Запрещено собирать окна вручную в Python и держать стили в коде.
- Темы: `resources/main.qss` (тёмная) и `resources/light.qss` (светлая, та же фиолетовая палитра). Новые диалоги оформляются теми же object-name/свойствами, что и `main_window.ui`, и должны читаться в обеих темах.
- `main_window.py` — контроллер: сигналы/слоты, без прямых вызовов пакетных менеджеров. `settings_dialog.py` — только чтение/запись полей диалога, настройки хранит `config.py` (QSettings).
- Панель задач слева (`tasksPanel`, шаблон `ui/task_item.ui`) обновляется через `set_tasks()`/`set_task_context()`; не создавать отдельное окно плана.
- Чаты создаются динамически из `ui/chat_item.ui`, история хранится в `<data_dir>/chats.json` (`chat_store.py`). Удаление — кнопкой `×` или через ПКМ, всегда с подтверждением. После удаления последнего чата колонка закрывается, а новый чат создаётся при первом запросе. Имя нового чата сейчас — первые 40 символов запроса (заглушка); позже LLM будет сама придумывать короткое название.
- Долгие операции — в worker/QThread, главный поток GUI не блокировать.

## Поток выполнения

`запрос → планировщик → tool calls → проверка политики → dry-run (если нужен) → выполнение → проверка результата → отчёт`

Модель предлагает только вызовы инструментов из известного набора; исполняет их код приложения. Успех операции подтверждается фактической проверкой состояния системы (пакет установлен, файл существует/удалён), а не текстом модели.

## Безопасность (жёсткие правила)

- Модель не получает shell. Никаких `shell=True`, интерполяции строк в команды и произвольных команд от LLM. Только типизированные инструменты с валидацией аргументов; команды собираются как argv.
- Автономно, без подтверждений: поиск/чтение, `mkdir`, установка пакетов, обновление индекса, очистка кэша, dry-run.
- Только с подтверждением: удаление/перемещение пользовательских данных, удаление пакетов, изменение системных конфигов, всё необратимое или выходящее за пределы домашней директории.
- Неоднозначный запрос — уточняющий вопрос, а не подтверждение. «Удали все временные файлы» без папки и критерия не выполнять: нужен путь и критерий (например, `~/Downloads`, старше 30 дней).
- Не удалять файлы по предположению «это не нужно». Если действие обратимо — сначала корзина/бэкап.
- Защищённые пути: `/`, `/etc`, `/usr`, `/boot`, `/dev`, `/proc`, `/sys`, `/var/lib`. Рекурсивные операции по ним запрещены; проверять `realpath` и симлинки.
- Для root-операций — `pkexec`/polkit, а не `sudo` в терминале: GUI не должен блокироваться на вводе пароля.
- Каждое выполненное действие писать в audit log (JSONL) в `data/`: время, инструмент, argv, результат, код возврата.
- Не выдавать предположение за факт; при ошибке сообщать, что именно не сработало и что проверено.

## Дистрибутивы и пакетные менеджеры

| Семейство | Бэкенд |
|---|---|
| Debian / Ubuntu / Astra Linux | `apt` |
| Fedora / ROSA | `dnf` |
| Arch Linux | `pacman` |
| openSUSE | `zypper` |
| ALT Linux | `apt` (rpm-based); `epm` — опционально |

- Не хардкодить команды в GUI/агенте: каждый бэкенд реализует общий интерфейс (`is_installed`, `search`, `install`, `remove`, `update_index`, `clean_cache`).
- Автодетект по `/etc/os-release` — по умолчанию. Ручной выбор в настройках — override; при несовпадении с реальной системой агент предупреждает и не выполняет рискованные операции.
- ALT: `apt` нативный, `epm` может отсутствовать — проверять наличие, а не предполагать.
- ROSA: современная использует `dnf`; `urpmi` — legacy, не считать основным.
- «Поддержка дистрибутива» = детект + сборка команд + тесты, а не просто наличие класса.

## Модель и железо

- Модель не выбрана. Кандидаты для бенчмарка: Qwen2.5-3B-Instruct, Llama-3.2-3B-Instruct, Gemma-2-2B-it; при запасе RAM проверить 4B и русскоязычные варианты. Решение — только по замерам.
- Ноутбук: i5-6300HQ, ~8 ГБ RAM, GTX 950M (Maxwell, sm_50). GPU ноутбука не считать рабочей опцией: инференс — CPU, GGUF Q4, замерять tok/s и RAM.
- ПК для обучения: RTX 2070 8 ГБ, 16 ГБ RAM — QLoRA.
- 3B в Q4 занимает ~2 ГБ; 7–8B в Q4 — ~4,5–5 ГБ и при 8 ГБ RAM уйдёт в swap. Начинать с 3B.

## Научная часть

Цель — воспроизводимо показать преимущество дообученной модели над базовой, а не просто собрать агента.

- Датасет: JSONL, пример `{request, distro, expected_plan, tool_calls, risk, requires_confirmation}`.
- Сравнение base vs tuned на фиксированном held-out наборе; фиксировать seed, версии и конфиги, не переобучаться на eval.
- Метрики: валидность JSON/tool-call, правильность инструмента и аргументов, отказ от опасных действий, качество русского, latency и RAM на ноутбуке.
- Не удалять датасеты, конфиги и логи экспериментов. Чекпоинты и веса в git не коммитить; конфиги и eval-скрипты — коммитить.

## Тесты

- `pytest`; никаких реальных `apt`/`dnf`/`pacman`/`zypper`, сети и root.
- `subprocess` мокать; фикстуры `/etc/os-release` — в `tests/fixtures/os-release/`.
- Обязательные тесты: детект дистрибутивов, сборка argv, политика путей (symlink/`..`), решение о подтверждении, валидация tool-call.
- GUI-тесты — с `QT_QPA_PLATFORM=offscreen`, маркер `gui`; на первом этапе достаточно smoke-теста импорта/окна.
- Ответы модели не тестировать детерминированно: для этого `MockBackend`.

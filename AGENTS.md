# AGENTS.md — TuxAgent

Локальный русскоязычный ИИ-агент для Linux: понимает запросы на естественном языке, автономно выполняет безопасные системные задачи и запрашивает подтверждение только при необратимом риске. GUI — PyQt6.

## Источники истины

- `docs/TuxAgentTTv1.md` — техническое задание (черновик, но главный источник требований).
- `docs/*.docx`, `docs/*.pptx` — материалы защиты. Бинарные: не редактировать, не считать спецификацией. При расхождении с ТЗ верно ТЗ.

## Текущее состояние

Инфраструктура готова: `AGENTS.md`, `TODO.md`, раздельные requirements, `.venv` на Python 3.13. Кода приложения ещё нет. Следующие шаги — в `TODO.md`; не выдумывай реализацию, сначала создай её.

## Приоритеты

1. Сначала GUI и логика, не требующая GPU. Если GPU-машина недоступна, работать на `MockBackend`, а не ждать железо.
2. AppImage — финальный этап. Не тратить время на упаковку до работающего MVP.
3. Научная часть обязательна: нужно воспроизводимо показать, что дообученная модель лучше базовой. Красивая демка без сравнения цель не закрывает.

## Стек

- Python 3.13, Linux-only. Язык не менять.
- На dev-машине системный `python3` — 3.14: использовать `python3.13` и venv, не ставить зависимости глобально (PEP 668).
- GUI: PyQt6. Разметка — только `ui/*.ui` (Qt Designer), стили — только `resources/*.qss`. Запрещено собирать окна вручную в Python и держать стили в коде.
- Системный слой: дистрибутив определяется по `/etc/os-release`, пакетные менеджеры — только через общий интерфейс.
- Инференс: `LLMBackend` + llama.cpp/GGUF (CPU) для релиза, Ollama для экспериментов, `MockBackend` для тестов.
- Обучение: PyTorch + PEFT/bitsandbytes (QLoRA) только на ПК с RTX 2070. В runtime и AppImage ML-стек не попадает.

## Структура

```text
main.py                  # тонкий лаунчер
src/tuxagent/
  app.py                 # QApplication, загрузка .ui/.qss
  ui/                    # контроллеры окон (не разметка)
  core/                  # агентный цикл, планировщик, исполнитель
  llm/                   # base.py, mock.py, llama_cpp.py, ollama.py
  system/                # distro.py, package_managers/
  tools/                 # типизированные инструменты
  safety/                # политика, верификация, dry-run
ui/                      # *.ui
resources/               # *.qss, иконки
tests/                   # pytest, фикстуры
data/                    # runtime: логи, audit, кэш; в git не хранится
```

Модели хранить в `~/.local/share/tuxagent/models` (XDG), не в репозитории.

## Поток выполнения

`запрос → планировщик → tool calls → проверка политики → dry-run (если нужен) → выполнение → проверка результата → отчёт`

Модель предлагает только вызовы инструментов из известного набора; исполняет их код приложения. Успех операции подтверждается фактической проверкой состояния системы (пакет установлен, файл существует/удалён), а не текстом модели.

## Безопасность (жёсткие правила)

- Модель не получает shell. Никаких `shell=True`, интерполяции строк в команды и произвольных команд от LLM. Только типизированные инструменты с валидацией аргументов; команды собираются как argv.
- Автономно, без подтверждений: поиск/чтение, `mkdir`, установка пакетов, обновление индекса, очистка кэша, dry-run.
- Только с подтверждением: удаление/перемещение пользовательских данных, удаление пакетов, изменение системных конфигов, всё необратимое или выходящее за пределы домашней директории.
- Неоднозначный запрос — уточняющий вопрос, а не подтверждение. «Удали все временные файлы» без папки и критерия не выполнять: нужен путь и критерий (например, `~/Downloads`, старше 30 дней).
- Не удалять файлы по предположению «это не нужно». Если действие обратимо — сначала корзина/бэкап.
- Защищённые пути: `/`, `/etc`, `/usr`, `/boot`, `/dev`, `/proc`, `/sys`, `/var/lib`. Рекурсивные операции по ним запрещены; проверять `realpath` и симлинки.
- Для root-операций — `pkexec`/polkit, а не `sudo` в терминале: GUI не должен блокироваться на вводе пароля.
- Каждое выполненное действие писать в audit log (JSONL) в `data/`: время, инструмент, argv, результат, код возврата.
- Не выдавать предположение за факт; при ошибке сообщать, что именно не сработало и что проверено.

## Дистрибутивы и пакетные менеджеры

Матрица v1:

| Семейство | Бэкенд |
|---|---|
| Debian / Ubuntu / Astra Linux | `apt` |
| Fedora / ROSA | `dnf` |
| Arch Linux | `pacman` |
| openSUSE | `zypper` |
| ALT Linux | `apt` (rpm-based); `epm` — опционально |

- Не хардкодить команды в GUI/агенте: каждый бэкенд реализует общий интерфейс (`is_installed`, `search`, `install`, `remove`, `update_index`, `clean_cache`).
- Автодетект по `/etc/os-release` — по умолчанию. Ручной выбор в настройках — override; если он не совпадает с реальной системой, агент предупреждает и не выполняет рискованные операции.
- ALT: `apt` нативный, `epm` может отсутствовать — проверять наличие, а не предполагать.
- ROSA: современная использует `dnf`; `urpmi` — legacy, не считать основным.
- «Поддержка дистрибутива» = детект + сборка команд + тесты, а не просто наличие класса.

## Модель и железо

- Модель не выбрана окончательно. Кандидаты для бенчмарка: Qwen2.5-3B-Instruct, Llama-3.2-3B-Instruct, Gemma-2-2B-it; при запасе RAM проверить 4B и русскоязычные варианты. Решение — только по замерам.
- Ноутбук: i5-6300HQ, ~8 ГБ RAM, 4 ГБ swap, GTX 950M (Maxwell, sm_50). Современные PyTorch/CUDA-сборки Maxwell не поддерживают, bitsandbytes 4-bit требует sm_75+. GPU ноутбука не считать рабочей опцией: инференс — CPU, GGUF Q4, замерять tok/s и RAM.
- ПК для обучения: RTX 2070 8 ГБ, 16 ГБ RAM — QLoRA.
- 3B в Q4 занимает ~2 ГБ; 7–8B в Q4 — ~4,5–5 ГБ и при 8 ГБ RAM уйдёт в swap. Начинать с 3B.

## Научная часть

Цель — показать преимущество дообученной модели над базовой, а не просто собрать агента.

- Датасет: JSONL, пример `{request, distro, expected_plan, tool_calls, risk, requires_confirmation}`.
- Сравнение base vs tuned на фиксированном held-out наборе; фиксировать seed, версии и конфиги, не переобучаться на eval.
- Метрики: валидность JSON/tool-call, правильность инструмента и аргументов, отказ от опасных действий, качество русского, latency и RAM на ноутбуке.
- Не удалять датасеты, конфиги и логи экспериментов. Крупные артефакты (чекпоинты, веса) в git не коммитить; конфиги и eval-скрипты — коммитить.

## Команды

Окружение уже создано: `.venv` на Python 3.13, runtime и dev установлены. `main.py` пока пустой, тестов ещё нет — команды запуска начнут работать после этапа 1.

```bash
python3.13 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt   # runtime + dev
.venv/bin/python main.py
.venv/bin/pytest -q
.venv/bin/pytest tests/test_distro.py::test_detect_astra -q
.venv/bin/ruff check .
```

Для чистого runtime: `.venv/bin/pip install -r requirements.txt`.

## Зависимости

- `requirements.txt` — runtime (PyQt6 и минимально необходимое). Именно это попадает в AppImage.
- `requirements-dev.txt` — runtime + `pytest`, `pytest-qt`, `ruff`; начинается с `-r requirements.txt`.
- `requirements-ml.txt` — `torch`, `transformers`, `peft`, `bitsandbytes`, `datasets`/`accelerate`; только ПК с RTX 2070.
- Версии фиксировать после установки в venv. PyTorch и CUDA-зависимости не добавлять в runtime.
- На ноутбуке ставить runtime + dev; ML-стек на ноутбук не ставить.

## Тесты

- `pytest`; никаких реальных `apt`/`dnf`/`pacman`/`zypper`, сети и root.
- `subprocess` мокать; фикстуры `/etc/os-release` — в `tests/fixtures/os-release/`.
- Обязательные тесты: детект дистрибутивов, сборка argv, политика путей (symlink/`..`), решение о подтверждении, валидация tool-call.
- GUI-тесты — с `QT_QPA_PLATFORM=offscreen`; на первом этапе достаточно smoke-теста импорта/окна.
- Ответы модели не тестировать детерминированно: для этого `MockBackend`.

## Git и артефакты

- Ветка `main`, remote `origin` (GitHub).
- Все коммиты и push делает только владелец проекта. Агент не коммитит и не пушит.
- В git не попадают: `.venv/`, `__pycache__/`, `*.gguf`, `models/`, runtime-содержимое `data/`, чекпоинты, `*.AppImage`.
- `docs/*.docx` и `docs/*.pptx` — часть репозитория; не перезаписывать их автоматически.

## Стиль

- Идентификаторы и код — на английском; пользовательские строки, ошибки и отчёты — на русском.
- Публичные функции — с type hints; результат выполнения команд — dataclass, а не tuple/сырой stdout.
- Логи — через `logging`, не `print`. Долгие операции не выполнять в главном потоке GUI: worker/QThread.
